# 自动补货的履约对账与仓内处置仓

自动补货助手报告“已下单”只代表它发过请求：采购端可能拆成多笔确认、司机可能只送到一部分。
本项目把连接器、采购、收货、调拨和班组班次的交接文件沉淀为**同一批可追溯事实**，让采购看清
欠交量与可补单量，让仓库基于独占库存决定哪些拣配单能进入下一轮拣配。

合成交接资料位于 `examples/`，字段含义见 [交接资料说明](docs/exchanges.md)，
系统口径与三层架构见 [数据仓设计](docs/architecture.md)。

## 运行环境

Python 3.14.10，仅使用标准库（含 SQLite）。所有命令都可反复运行：

- 导入按**内容哈希**幂等（转发人不是业务身份，同一事实多人转发只算一次）；
- 更正通过追加原件后**重建派生层**生效，原始层只追加不改写；
- 班次发布与领用回执是持久事件，重复运行不会重复占用库存或重复入账。

读取不受信任的交接目录时通过 `python -I run.py ...` 以隔离模式运行，避免目录中植入的
同名模块被导入。

## 命令

| 命令 | 作用 |
| --- | --- |
| `init-db` | 初始化 SQLite 数据仓（默认 `data/warehouse.db`，`--db` 可改） |
| `import <文件或目录>` | 导入 CSV/TSV/JSONL 交接资料，结构不合格件写入 `raw_rejected` 留痕 |
| `rebuild` | 从原始层重建当前事实，登记无法可靠归属的冻结事件 |
| `publish-shift` | 按 `--as-of` 与 `--through-arrival` 发布班前拣配/补货交接文件 |
| `register-receipts` | 登记尚未入账的班组领用/退回回执，过期或超额版本明确拒绝 |
| `export-procurement` | 导出采购履约 CSV（欠交、待核实、可补单） |
| `export-remediation` | 导出补救队列 CSV（已领单的货位短数与可补救量） |
| `status` | 输出采购、库存桶、冻结、补救、班次与凭证的当前事实 |
| `trace request <请求号>` / `trace pick <拣配单号>` | 并排追溯原单、当前事实、班次使用与已核实补救结果 |

## 一键演示

```bash
./demo.sh
```

脚本清空库后按接收批次重放完整周期，产物在 `out/demo/`：

- `shifts/S{1,2,3}_pick_handoff.csv`：每次班前的拣配承诺与未发布原因，每行可追到上架凭据；
- `shifts/S*_replenish_handoff.jsonl`：采购履约事实与冻结登记；
- `shifts/S*_manifest.json`：班前时刻、截至批次、被取代的旧承诺与各源最大批次；
- `procurement.csv`、`remediation.csv`：采购与补救视角的汇总交接文件。

演示时间线：

1. **S1（截至批次 3）**：G711 的 12 件 PEN 整单配齐 K31（8）与 K33（4），班组领取 W3；
2. **批次 4/5 更正**：G711 修订为 7 件、另隔离 5 件；尚未领走的 K33/K34 重评为短配，
   S1 未领承诺被取代；已领的 K31 保留凭证，按货位产生 1 件短数进入补救队列；
3. **批次 6**：G714 上架 9 件、调拨 T03 入位、班组退回 2 件；**S3** 重新配齐 K32/K33/K34，
   K31 短数随退回清零。
