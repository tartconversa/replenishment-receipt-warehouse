# 履约数据仓设计

## 三层数据

| 层 | 表 | 性质 | 重跑行为 |
| --- | --- | --- | --- |
| 原始层 | `raw_*`、`raw_rejected` | 只追加的交接原件 | 按规范化内容哈希去重，重复导入跳过 |
| 派生层 | `cur_*`、`stock_bucket`、`freeze_event` | 当前事实 | 每次 `rebuild` 清空后按 `arrival, raw_id` 确定性重放 |
| 持久层 | `shift_publication`、`shift_promise`、`shift_decision`、`issue_ledger`、`holding_ledger` | 班次与领用事件 | 业务事件，重跑不重复生效 |

原始层记录全部事实（含 `hold`、`refused`、`in_transit`、`canceled`、`timeout`），
任何业务逻辑都不改写原件；派生层可以随时丢弃重建；持久层引用上架凭据号
（`evidence_kind + evidence_id`）而非易变的桶号，因此派生层重建后历史承诺仍可追溯。

## 采购口径

- **行级对应**：采购确认按 `(po_line, revision, request)` 归属。同一外部行可以正常拆分给
  多个请求，也可以合并回复多个请求；只有同一请求在同一修订下出现互相矛盾的数量/状态、
  归属 SKU 不一致，或引用了不存在的请求，才冻结整行。
- **修订覆盖**：`revision` 高版本覆盖低版本；收货 `receipt` 同理取最高修订。同修订号的
  重复件内容不一致才判冲突。
- **销欠**：只有 `available` 且未冻结的合格收货才能销欠；`hold`、`refused`、在途都不销欠。
  一个外部行服务多个请求时，合格收货与拒收量都按请求号升序消化。
- **欠交量** `backordered = max(confirmed − qualified_received, 0)`。
- **待核实**：目标量中未收到任何确认（confirmed/canceled）的余量
  `in_flight_unknown = target − answered`。`timeout` 仅代表连接器未见回执，供应商仍可能
  接受，这部分单列待核实，**绝不进入可补单量**；后续若收到确认则待核实归零。
- **可补单量**：只承认两类明确落空且无其他保障的缺量——明确取消的余量、明确拒收且未被
  后续合格收货覆盖的余量；每类再扣减已确认调拨（内部保障）与结果未知余量。仍处于已确认
  状态的欠交（隔离、延迟上架、在途）有在途保障，不能补单。

## 库存与货位口径

- 只有验收合格且完成上架（收货 `available`，或调拨推进到 `available`）且未冻结的数量进入
  货位库存桶；`hold`、`refused`、`in_transit` 在两端都不可用。
- 每个桶可逐件追溯到上架凭据（收货号或调拨号）与采购行。
- 桶的可承诺量 = 桶总量 − 班组持有（领走未退回）− 未领走的活跃承诺。同一件库存不能同时
  留给两张单。
- 已确认调拨（含在途）作为采购需求的内部保障参与补单扣减，但入位前不进入货位池。

## 班次与承诺口径

- 班前清单只纳入 `due >= as_of`、`arrival <= through_arrival` 且未冻结、未领取的需求；
  排序为货位 → 业务优先级（小者优先）→ 领料期限 → 单号 → SKU，桶内按上架先后 FIFO。
- **整单配齐**才发布；任一行不足则整单不发布，决策表记录 `short` 与原因，但不落承诺、
  不占库存。过期限需求记 `expired_demand`，冻结行记 `frozen`。
- 新班次发布时，所有未领走的旧承诺置 `superseded=1` 并在清单 manifest 中登记；班组拿过期
  版本或超量领取时，`issue_ledger` 明确记录 `rejected` 与原因。
- 已领取的单不再参与新班次，由补救队列跟踪。

## 领用回执与补救口径

- `collected` 必须匹配当前未取代承诺的货位/SKU/数量；同一 issue 重复领取只入账一次。
- `returned` 必须有对应的未退回持有，且退回量不超过持有余量；只有班组回执确认退回的货
  才回到可用池。
- 持有台账同时记录领取批次 `arrival` 与退回批次 `return_arrival`，因此补救队列支持任意
  `through_arrival` 时点复盘。
- 短数 = 班组仍持有的量中，上架凭据在该时点已无法支撑的部分（更正把 available 改成
  hold/冻结、或桶总量下降时产生）；`remediable_free_units` 给出同货位当前可用于补救的余量。

## 冲突冻结

无法可靠归属的冲突按最小影响面冻结，并在 `freeze_event` 记录原因与原件 `raw_id` 证据：

- 采购行同修订矛盾、SKU 归属冲突、引用未知请求 → 冻结采购行，其关联收货一并冻结；
- 收货同修订矛盾、引用未知采购行、SKU 与采购行不一致 → 冻结该收货凭据；
- 调拨引用未知请求或 SKU 不符 → 冻结该调拨；
- 同一拣配行出现互相矛盾的原件 → 冻结该拣配行。

冻结只影响被点名的供给与需求，其他货位照常出单；冻结实体不进入任何汇总数字，只在冻结视图
与补货交接文件中显式暴露。

## 交接文件产物

每次 `publish-shift` 在输出目录生成：

- `<shift>_pick_handoff.csv`：承诺行（含 `evidence_kind/evidence_id`）与未发布决策；
- `<shift>_replenish_handoff.jsonl`：逐请求采购履约事实 + 冻结登记；
- `<shift>_manifest.json`：班前时刻、截至批次、被取代承诺 ID、各源最大接收批次。

`trace request|pick` 把数字并排回溯到三层：原始 `raw_*` 记录、重建后的当前事实、
班次承诺/决策与领用凭证/补救结果。
